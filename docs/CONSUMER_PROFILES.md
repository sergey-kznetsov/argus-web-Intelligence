# ARGUS consumer profiles and tool packs

## Purpose

ARGUS is one standalone web-intelligence backend shared by multiple analytical modules.
The crawler/runtime, Evidence/Provenance, storage, queue, security and recovery layers remain
universal. Each product consumer receives a separate versioned research contract and a
separate versioned tool pack.

The hierarchy is:

```text
consumer module ID
  -> ConsumerProfileRegistry
  -> capability
  -> requested facts
  -> ToolPackRegistry
  -> planner / recipe / extractor policy
  -> allowed source adapters
  -> FAST -> BROWSER -> AGENT
  -> Observation / Evidence / Provenance
```

This prevents Kraken, Janus, Historical and future consumers from being treated as one
undifferentiated scraper while avoiding consumer-specific `if/elif` branches in ARGUS Core.

## CollectionRequest fields

Profiled consumers use the stable module ID in `consumer` and may supply their versioned
consumer contract:

```json
{
  "consumer": "kraken.development.uds",
  "consumer_profile_version": 1,
  "capability": "urban_signals",
  "requested_facts": [
    "complaint",
    "public_appeal",
    "post",
    "comment"
  ]
}
```

ARGUS resolves and stores two additional server-owned execution fields:

```json
{
  "tool_pack_id": "kraken.urban_signals",
  "tool_pack_version": 1
}
```

A caller may repeat these fields when replaying a persisted request, but it cannot select a
different pack or version. A mismatch is rejected before the Collection enters the queue.

`intents`, territory and constraints continue to describe research goals and operational
limits. `capability` and `requested_facts` define the factual result contract. The tool pack
defines which ARGUS tooling is allowed to execute that contract.

## Tool pack contract

A tool pack contains execution policy, not downstream analytics:

```text
tool_pack_id
version
consumer_id
capability
allowed_source_ids
shared_tools
planner_policy
recipe_namespace
extractor_policy
```

Shared tools may include FAST, BROWSER, AGENT, Evidence, Provenance and snapshots. A tool
pack references them; it does not duplicate their implementation.

Consumer-exclusive adapters, source routes, recipes and extraction policies are enabled only
by the pack that owns them. For example a residential-registry adapter may belong to a Janus
building-demographics pack without becoming available to Kraken.

## Runtime isolation

Tool-pack selection is enforced while the Collection is executing, not only when the request
is validated.

ARGUS activates the resolved pack in an async `contextvars` scope for the Collection. The
SourceRegistry reads that scope when:

1. initial adapters are selected for the requested intents;
2. a discovery result asks for an adapter;
3. a child task generated by another source asks for an adapter.

A source ID outside the active pack is rejected before its adapter can fetch anything.
`contextvars` means concurrent Collections keep independent tool-pack state even when they are
executed by the same worker process.

This is the hard boundary that prevents one module's special tooling from leaking into another
module's research run.

## Durable execution identity

The Collection request persists:

```text
consumer
consumer_profile_version
capability
requested_facts
tool_pack_id
tool_pack_version
```

The orchestrator checkpoint additionally records `consumer_execution_contract` with:

```text
contract version
consumer ID / profile version
capability / requested facts
tool pack ID / version
planner policy
recipe namespace
extractor policy
shared tools
```

Actual source adapters used by the Collection remain visible in normal `coverage`,
Observation/Evidence provenance and source-specific snapshots. SiteRecipe and extractor
versions remain attached to their normal Evidence/provenance paths.

This makes a historical run explainable without guessing which generation of consumer tooling
was active.

## Initial Kraken profile

The first product profile is:

```text
consumer: kraken.development.uds
profile version: 1
default capability: urban_signals
tool pack: kraken.urban_signals v1
```

Allowed factual types:

```text
complaint
public_appeal
post
comment
resident_message
local_news_mention
incident_mention
```

Kraken follows the upstream SOIKA subject domain: text messages and public appeals by citizens
about urban issues and socially relevant events. Typical subjects include housing and communal
services, landscaping, safety, transport, roads, healthcare, education, social protection,
construction, waste management, ecology and energy.

Business or venue reviews are deliberately outside the Kraken factual contract. A restaurant,
shop, office, institution or other nearby POI may be used as a source-backed spatial anchor to
establish where a social problem occurred, but ARGUS must not turn that POI into a Kraken
research subject and must not crawl its customer reviews on Kraken's behalf. Curated public-map
review research is therefore disabled for the `urban_signals` ToolPack even though the generic
ARGUS backend retains that capability for other consumers.

The Kraken tool pack currently allows the shared factual/navigation sources required for urban
signals:

```text
generic_web
rss_atom
json_feed
site_discovery
openstreetmap_overpass
```

Residential-registry and historical-only adapters such as `mingkh_residential` and
`pastvu_historical` are deliberately outside this pack.

ARGUS owns discovery, acquisition, Evidence/Provenance, snapshots and storage. Kraken owns
interpretation, classification, geospatial-semantic analysis, event formation,
activity/risk calculation and its final Geo Analyzer report section.

## Legacy migration rule

Legacy consumers that send only the old fields remain temporarily accepted without a tool
pack. This compatibility path is intentionally narrow:

- an unregistered consumer may use the old `consumer + intents` contract;
- an unregistered consumer may not send profiled contract fields;
- an unregistered consumer may not select a tool pack;
- once a product module is migrated, it must use its registered stable module ID, capability
  and tool pack.

Legacy compatibility is not the target architecture for new modules.

## Adding a new analytical module

A new module must be integrated without editing ARGUS Core control flow.

The implementation sequence is:

1. define the module's stable `consumer_id`;
2. define one or more capabilities and allowed factual result types;
3. create one versioned tool pack for each capability;
4. list the shared and consumer-exclusive source adapters required by that pack;
5. define planner, extractor and SiteRecipe namespace policies;
6. register the capability in `ConsumerProfileRegistry` with its `tool_pack_id`;
7. register the corresponding pack in `ToolPackRegistry`;
8. add any new adapters/extractors/recipes through their normal ARGUS extension contracts;
9. add contract, source-isolation and end-to-end tests;
10. deploy a pinned CI-green ARGUS release before enabling the new module in Geo Analyzer.

Adding a module must not require code such as:

```python
if consumer == "kraken":
    ...
elif consumer == "janus":
    ...
```

The consumer registries contain declarations. Scraping/navigation/extraction code stays in its
normal adapter/planner/recipe implementation and is selected through the pack.

## Planned consumers

Janus and Historical must receive their own product profiles and packs when their real module
input contracts are finalized.

Expected direction:

```text
Janus
  -> building_demographics
  -> residential premises / apartments / residents / management data
  -> dedicated housing-registry and public housing-portal tooling

Historical
  -> territory_history
  -> archives / old maps / historical photos / past organizations / dated events
  -> dedicated archive and temporal-research tooling
```

A tool useful to multiple consumers should remain a shared ARGUS tool and be referenced by
multiple packs. A source or recipe whose semantics are consumer-specific must stay in the
owning pack.

## Design rule

The registry is routing and contract metadata. It must never become a second place for
business analytics. ARGUS returns facts with Evidence/Provenance; analytical modules remain
responsible for conclusions.
